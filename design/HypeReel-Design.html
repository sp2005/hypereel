Track 2 · LangChain + LangGraph Bring-your-own use case Free model stack Built with Claude Code

One-page overview of the design that follows. The recipe library shows example domains to illustrate that recipes are pluggable; v1 ships the basketball recipe with an architecture-walkthrough stub (see §11 Scope).

1 · The one-liner

My agent helps a player or coach turn a full 60-minute game recording into a share-ready highlight reel matching a plain-language brief (one player, a whole team, only threes, no steals) in a Streamlit web app, replacing the 3–4 hours of manual scrubbing and clip-cutting in a video editor it takes today. It ingests the video, detects and scoreboard-confirms the right plays, and critiques and re-cuts its own reel on its own using ~6 tools (yt-dlp, frame sampling, scoreboard CV, a vision model, an LLM judge, and ffmpeg), hands off to a human to approve the clip list before it renders and again before it shares, and I'll know it works when a user gets a watchable, single-team reel in under 30 minutes that they'd actually post 8 times out of 10.

2 · The Agent Framework

FieldDecision
Agent goalTurn a raw video + a recipe into a time-boxed, share-ready highlight reel.
SurfaceStreamlit web app (chat-like input + review panel). CLI for scripted/demo runs.
Ordered steps1) plan strategy from the recipe & what the video offers → 2) resolve & download source → 3) propose candidate windows (audio + motion) → 4) confirm/score windows with a vision model → 5) score & select to the time budget → 6) human approves clip list → 7) render → 8) human approves share → 9) deliver/upload.
Tools read source resolver (yt-dlp/local), read audio-peak detector, read motion detector, read vision classifier/scorer, read clip selector, read renderer (writes a local file), write share/upload (behind a human gate).
MemorySession (LangGraph ReelState + in-memory checkpointer): candidates, classifications, selected clips, approval flags. Persistent (local JSON file): user profile — jersey #, team colors, preferred moment types, default length, target platform — plus learned preferences from accept/reject feedback. (A durable store like SQLite is a drop-in swap; the current build persists to JSON.)
Never doNever upload/post without explicit approval. Never fabricate a moment label it isn't confident about (grounding). Never center non-subject minors (privacy). Never include recipe-listed exclusions (timeouts, bench, shaky pans…).
Human-in-the-loopGate 1 — approve/reorder/drop the candidate clip list before render. Gate 2 — approve before any share/upload (write action). Plus a self-correction gate when highlights underfill the budget.
On failureDownload fails → retry w/ backoff → ask for another link/local file. Vision errors → degrade to audio+motion score. Subject never found → ask to confirm jersey #, or fall back to team-level. Underfilled budget → ask: ship shorter / lower threshold / add footage.
Success metricUser gets a reel they'd actually post 8/10 times, in <10 min, from a single link — end-to-end task completion, not single-shot accuracy.

3 · Architecture

Recipe-driven LangGraph state machine. Cheap local signals propose, the vision model confirms, deterministic code selects, and humans gate the two write-ish actions. The layered diagram below runs top-down: two interfaces feed a single LangGraph agent (one shared ReelState), which sits on a state/memory layer, a swappable model layer, a tool layer, and the external services it calls. The judge → select revision loop is the one place the agent critiques and re-cuts its own output.

4 · The Recipe (the intellectual core)

A recipe is the agent's declarative policy: it defines what counts as a highlight, how to find it, who to focus on, and how to assemble the reel. The same schema generalizes across domains; the pivotal field is:

highlight_model: event_based | quality_based | hybrid
event_based (basketball): cheap signals propose discrete moments → vision model confirms the event + subject. quality_based (architecture): no discrete events — sample windows and have the vision model score them against a natural-language scoring_rubric; sustained high-scoring windows become clips. This one switch is how the design handles abstract, non-standardized domains.

6 · State & memory

Session (per run)
LangGraph ReelState + in-memory checkpointer
  • candidates, classifications (1:1)
  • scored & selected clips, proposed duration
  • gate flags: needs_human, human_gate, approved, shared
  • errors, notes, mode (mock/live)
Checkpointer also enables resuming an expensive extraction — handy for the live demo.
Persistent (across runs)
local JSON file (SQLite/mem0-swappable)
  • profile: jersey #, team colors, default length, platform
  • preferred moment types
  • learned prefs from accept/reject (e.g. "more 3-pointers, drop free throws")

7 · Human-in-the-loop boundary

Reads run autonomously; the two write-ish actions are gated, implemented with LangGraph interrupts:

  1. Gate 1 — before render: the agent presents the proposed clip list (timestamps, moment type, why chosen, subject-present). The human approves, reorders, or drops clips. Edits feed the preference learner.
  2. Gate 2 — before share: rendering a local file is fine autonomously; posting to a platform is a write action and always requires explicit approval.

11 · Scope

In scope (v1)
  • One recipe deep: AAU basketball, jersey# + team-color
  • YouTube ingestion (+ local fallback)
  • audience switch (individual ↔ team)
  • full agentic layer: planner, conditionals, 2 HITL gates, self-correction, failure recovery
  • architecture recipe as a config stub (proves generalization)
Out of scope / future
  • real social-platform upload (gate is built; connector stubbed)
  • full-length game live processing (runs offline; demo uses a short clip)
  • LLM recipe scaffolding from prose
  • face-recognition subject match
  • trend dashboards across many reels
